# ПОС — Преподавательская Оценка Студентов

Консольный модуль оценивания: студенты, рубрикатор критериев, оценки, итоговый балл по весам и выгрузка итогов. Сделан на DDD, архитектуре **Ports and Adapters** и паттернах GoF.

## Запуск

Нужен .NET 10 SDK.

```bash
dotnet run --project src/Pos.ConsoleApp              # интерактивное меню
dotnet run --project src/Pos.ConsoleApp -- --demo    # сквозной демо-сценарий без ввода
dotnet test                                          # юнит-тесты
```

Демо-сценарий выполняет всю цепочку из ТЗ: рубрикатор и студенты → оценки → попытки нарушить правила → исправление и отмена → итог по двум правилам → экспорт в `export/final_grades.csv` и `export/final_grades.json`. В интерактивном меню его можно запустить пунктом 1.

## Язык предметной области → код

| Слово из ТЗ | Тип в коде | Что это |
|---|---|---|
| студент | `Student` (Entity), `StudentName` (VO) | кого оценивают |
| критерий | `Criterion` (Entity внутри агрегата), `CriterionName`, `Weight` (VO) | за что ставят балл, максимум и вклад в итог |
| рубрикатор | `Rubric` (корень агрегата) | набор критериев курса |
| балл | `Score` (VO) | значение вместе с максимумом критерия |
| оценка | `Evaluation` (Entity) | «этому студенту по этому критерию поставили такой балл», с датой и комментарием |
| итог | `FinalGrade` (VO), `FinalGradeCalculator` (Domain Service) | результат по студенту, вычисляемый из оценок и рубрикатора |

## Карта DDD

**Entity и Value Object.**
- `Student` и `Evaluation` — **Entity**. У них есть идентичность (`StudentId`, `EvaluationId`), и они живут во времени: студента можно переименовать, оценку исправить, но это всё тот же студент и та же оценка.
- `Score`, `Weight`, `StudentName`, `CriterionName`, `FinalGrade` и все `…Id` — **Value Object**. У них нет идентичности, они неизменяемы, сравниваются по значению и сами себя проверяют.

Пример: два `Score(8, 10)` равны, а два студента с одинаковым именем — разные люди.

**Агрегат `Rubric`.** Критерии создаются только через `Rubric.AddCriterion` (конструктор `Criterion` — `internal`). Поэтому рубрикатор гарантирует уникальность названий (без учёта регистра), положительный максимум и положительный вес.

**Инварианты из ТЗ и где они охраняются:**

| Правило | Где |
|---|---|
| балл не выходит за пределы критерия | `Score` (не создаётся вне `[0; max]`), `Evaluation.Correct` (проверяет новый балл через `Score.WithValue`) |
| оценка только по критерию из рубрикатора | `EvaluationFactory.Create` → `Rubric.GetCriterion` (иначе `DomainException`); `FinalGradeCalculator` ещё раз проверяет, что все оценки из рубрикатора |
| итог согласован с текущими оценками | итог **не хранится**: `FinalGradeCalculator` всегда считает его из текущих оценок; при удалении критерия или студента удаляются и их оценки |
| одна оценка на студента по критерию | `PosFacade.Grade` (для другой нужно исправление) и `FinalGradeCalculator` |

**Repository (порты).** Интерфейсы `IStudentRepository`, `IRubricRepository` и `IEvaluationRepository` лежат в домене, а их реализации (in-memory) — в Infrastructure.

**Domain Service.** `FinalGradeCalculator`: итог зависит сразу от студента, рубрикатора и набора оценок, поэтому не принадлежит ни одной сущности.

## Архитектура: Ports and Adapters

```
src/
  Pos.Domain/          ядро: Entity, VO, агрегат, инварианты, Domain Service, порты-репозитории
  Pos.Application/     сценарии (PosFacade), DTO-представления, порт IGradeExporter
  Pos.Infrastructure/  адаптеры: in-memory репозитории, CSV/JSON-экспорт, DI-контейнер
  Pos.ConsoleApp/      входной адаптер (консольное меню, демо) + composition root
tests/
  Pos.Tests/           xUnit-тесты
```

Направление зависимостей (только внутрь):

```
Pos.ConsoleApp ──► Pos.Infrastructure ──► Pos.Application ──► Pos.Domain
       └───────────────────────────────────────┘
```

Каждый слой — отдельный проект, поэтому направление зависимостей проверяет компилятор: `Pos.Domain` не ссылается ни на что, и в нём нет ни консоли, ни файлов, ни CSV. Консоль обращается только к `PosFacade` и получает DTO (`StudentView`, `FinalGradeView` и т. д.), а не доменные объекты. Конкретные реализации портов выбираются в одном месте — `CompositionRoot`.

## Паттерны GoF

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Factory** | `Domain/Evaluations/EvaluationFactory` | Единственная точка создания оценки: в ней проверяются оба правила (критерий из рубрикатора, балл в диапазоне). Обойти её нельзя — конструктор `Evaluation` `internal`. |
| Порождающий | **Builder** | `Domain/Rubrics/RubricBuilder` | Рубрикатор задаётся целиком (`PosFacade.SetupRubric`): если хоть один критерий плохой или список пуст, наружу не попадает «полусобранный» рубрикатор. |
| Структурный | **Facade** | `Application/PosFacade` | Одна точка входа во все сценарии. Консоль не знает о репозиториях, фабрике и расчёте и не дублирует логику сценариев. |
| Структурный | **Decorator** | `Domain/Grading/RoundingGradingPolicy` | Округление навешивается на любое правило итога. Правило расчёта и правило округления комбинируются независимо, без копий каждой стратегии «с округлением». |
| Поведенческий | **Strategy** | `IGradingPolicy`: `WeightedGradingPolicy`, `EvaluatedOnlyGradingPolicy` | Сменяемое правило итога в Domain Service: «итоговая» (пропуск = 0) и «текущая» (только выставленные критерии). Переключается в меню (пункт 13). |
| Поведенческий | **Template Method** | `Infrastructure/Export/GradeExporterBase` | Общий каркас выгрузки (проверка → папка → содержимое → запись файла); `CsvGradeExporter` и `JsonGradeExporter` меняют только формат. |

## Как считается итог

Шкала 10 баллов. Для каждого критерия берётся доля `балл / максимум`, умножается на вес, и всё нормируется на сумму весов (поэтому веса не обязаны давать в сумме 1):

```
итог = 10 · Σ(вес_i · балл_i / max_i) / Σ вес_i
```

- **Итоговая** (`weighted`): сумма весов по всем критериям рубрикатора, невыставленный критерий считается нулём.
- **Текущая** (`current`): сумма весов только по выставленным критериям.

Оба правила обёрнуты в округление до 2 знаков (половина округляется вверх).

## DI-контейнер

Используется самописный `DIContainer` (`Infrastructure/DependencyInjection`) из ДЗ1: transient, singleton и готовые экземпляры. Граф собирается в `ConsoleApp/CompositionRoot`. Тест `CompositionRootTests` проверяет, что весь граф разрешается.

## Тесты

`dotnet test` прогоняет:
- `ValueObjectTests`, `RubricTests`, `EvaluationTests` — инварианты: балл вне диапазона, критерий не из рубрикатора, дубликаты, пустые имена, исправление без потери старого значения;
- `FinalGradeCalculatorTests` — Domain Service, обе стратегии и декоратор округления;
- `PosFacadeTests` — сценарии через фасад: согласованность итога после исправления и отмены, каскадное удаление, смена правила;
- `ExporterTests` — CSV и JSON;
- `CompositionRootTests` — DI-граф, демо-сценарий целиком и выход из меню.
